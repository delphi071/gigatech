# 홈페이지 신규 구축 요구사항·기술 의존성 분석

- 작성일: 2026-09-26
- 담당: architect / build_requirements
- 범위: 제공 자료에서 구축 범위와 결정 사항을 분석한다. 스택·API·DB·디자인의 확정 명세와 제품 구현은 후속 단계다.
- 기준: 사용자가 지목한 `페이지 메뉴 구성안.xlsx`를 우선한다. `디자인중.xlsx`, 수정 요청문, 양식 이미지는 별도 요구 근거다. 자료 간 작성·승인 순서는 확인되지 않았다.
- 원본과 팀 설정은 변경하지 않았다. 기술 스택 설정, 제품 코드, 확정 디자인 명세가 없는 상태에서 기술 대안을 제시한다.

## 1. 판단 요약

기준안은 **회사소개·주요업무·장비보유현황의 3개 대메뉴와 5개 하위 메뉴**다. 우선 **홈 + 5개 콘텐츠 화면 + 공통 연락 동선**을 신규 제작하는 안이 적절하다. 홈의 구성과 대메뉴별 별도 소개 화면 추가 여부는 제안이며 아직 확정하지 않았다.

견적·고객문의 양식과 카카오 채널의 흔적은 있지만 기준 메뉴에는 없다. 따라서 문의폼·게시판·관리자 화면을 현재 필수 범위로 계산하지 않는다. 운영 방식을 선택한 뒤 필요한 서버·저장소·인증만 설계한다. 자료에 일반 회원가입·회원 마이페이지·결제 요구는 없다.

현재 가장 큰 선행 조건은 **정보통신설비 성능점검의 실제 서비스 설명, 회사 인증서, 최신 회사정보, 문의 접수 방식, 콘텐츠 수정 담당자**다. 외부 공식 설명만으로 회사의 등록·자격·보유장비·수행실적을 입증할 수 없다.

사이트 내부 검색은 기준안에 없다. 5개 하위 메뉴 수준에서는 메뉴·본문 구조를 먼저 설계하고, 자료실이나 게시글 수가 늘어 검색 필요가 확인되면 추가한다. 검색엔진 노출을 위한 페이지 제목·설명·사이트맵은 별도의 기본 품질 항목이다.

## 4. 선택 운영 기능과 서버·DB·인증 필요성

| 운영 시나리오 | 실제 근거·확정 상태 | 필요한 구성 | 필요하지 않거나 미정인 구성 |
| --- | --- | --- | --- |
| 소개 페이지 + 전화/이메일/카카오 연결 | 소개 페이지는 기준안. 연락 링크는 제안 및 S4 단서 | 정적 호스팅, HTTPS, 콘텐츠 배포 절차. 방문자는 외부 연락 수단으로 이동 | 자체 업무 서버·업무 DB·방문자 로그인 불필요. 카카오 API 로그인 연동도 링크만 제공하면 불필요 |
| 소개 페이지 + 비공개 문의/견적 접수 | S5/S6의 양식 근거. 현재 범위 채택은 미정 | 서버 측 검증·접수 처리 또는 선정한 외부 폼 서비스, 수신 담당자, 실패 확인 절차 | 일반 회원가입 불필요. 별도 DB는 보관·이력·중복 방지·접수 증빙 요구에 따라 결정. 외부 서비스 사용 시 자체 DB를 생략해도 그 서비스의 저장·삭제·권한 설정은 필요 |
| 담당자가 문의 상태·파일을 관리 | 직접적인 관리자 요구는 미확인 | 비공개 접수 저장소, 담당자 인증·권한, 조회·상태 변경·보관기한 처리, 파일 접근 제어 | 관리자 UI가 없더라도 수신함/외부 서비스의 접근 권한은 운영자가 관리해야 함 |
| 공지/자료실을 담당자가 직접 수정 | S2 확장안에 따른 선택 기능 | CMS 또는 관리자 편집 기능, 게시글·첨부 관리, 발행 상태·미리보기, 운영자 인증 | 게시글을 개발 담당자가 파일로 갱신한다면 별도 DB 없이 정적 발행 가능. 공개 댓글·누구나 글쓰기 요구 없음 |
| 온라인채팅 | S3의 두 탭 분리 요청, S4의 카카오 링크 | 단순 카카오 채팅 이동인지 별도 상담 서비스인지 먼저 결정 | 자체 실시간 채팅 서버·웹소켓·상담 이력 시스템은 근거 없이 추가하지 않음 |

카카오 채널과 채팅 URL은 공개 링크의 단서다. 채널 관리자 소유권, 현재 운영 여부, 응답 담당자와 상담시간은 추가 확인 대상이다. 채널을 실제로 변경하거나 메시지를 발송하지 않았다.

### 4.1 양식 이미지에서 읽은 요구

**견적요청양식(S5)**

- 별표가 있는 항목: 건물명, 담당자, 연락처, 이메일.
- 그 외 표시 항목: 주소·우편번호 검색, 대상설비 복수 선택, 요청사항, 양식 다운로드, 첨부파일, 개인정보 수집·이용 동의, 등록 버튼.
- 대상설비는 냉난방·환기·급수·배수·자동제어 등을 다루는 기계설비 항목이다. 이를 정보통신설비 항목으로 간주하지 않는다.
- 다운로드 안내는 별도 문서양식 작성을 언급하지만, 이 분석에서 사용 가능한 실제 다운로드 양식 파일을 확보하지 못했다. 빈 버튼으로 제공하면 안 된다.
- 파일 첨부 UI에는 파일 유형·개수·크기 제한이 표시되지 않는다. 파일명의 더블클릭 삭제 방식은 모바일·키보드 사용을 고려해 명시적인 삭제 버튼으로 재설계하는 안을 제안한다.

**고객요청양식(S6)**

- 별표가 있는 항목: 회사명, 성함/직급, 연락처, 이메일, 수신방법, 제목.
- 수신방법: 전화요망·이메일·방문요청. 내용 입력, 개인정보 수집·이용 안내와 동의, 등록 버튼이 있다.
- 방문요청은 연락 방식 선택일 뿐 자동 예약·일정 확정 요구의 근거는 아니다.
- 두 양식의 이메일·전화번호 분리 입력 UI는 재현할 필수 기능으로 보지 않는다. 단일 입력과 이해하기 쉬운 검증 메시지를 제안한다.

별표 표시는 원본 UI의 관찰 사실이며 신규 사이트의 필수 수집 항목을 확정하지 않는다. 필요한 최소 연락 수단과 상담 업무를 기준으로 필수·선택을 다시 정해야 한다. 이미지 속 동의문에는 수집항목·보유기간의 모호한 표현이 있어 그대로 전재하지 않는다. 최신 법령과 실제 처리 흐름에 맞는 담당자 검토 또는 별도 법무 확인이 필요하다.

### 4.2 폼을 채택할 경우 확정할 접수 계약

아래는 후속 기술 설계에서 사용할 **후보 계약**이다. 이 문서가 API나 DB를 승인한 것은 아니다.

| 항목 | 후보 계약 | 확정 전 결정 |
| --- | --- | --- |
| 일반 문의 | `POST /api/inquiries`, JSON: 회사명·담당자/직급·연락처·이메일·수신방법·제목·내용·동의문 버전/동의 여부 | 필수 필드, 글자 수, 지원 문자, 수신방법 값, 연락처 검증 범위 |
| 견적 접수 | `POST /api/quote-requests`, JSON 또는 multipart: 건물명·담당자·연락처·이메일·주소·대상설비 ID 배열·요청사항·동의 정보·선택 첨부 | 기계/정보통신 구분, 설비 코드, 주소검색 공급자 사용 여부, 파일 전달 방식·유형·크기·개수 |
| 성공 응답 | 영속 접수 기록이 생성되는 방식이면 `201`과 접수 ID. 내구성 있는 대기열 접수 방식이면 `202`와 접수 ID·접수 상태 | 저장/메일 전달/담당자 수신의 어느 시점을 성공으로 표시할지. 메일 전송 요청만으로 수신 완료라고 표시하지 않음 |
| 오류 응답 | 통일된 오류 코드·사용자 안내·필드 오류. 예: `400/422` 입력 오류, `413` 크기 초과, `415` 파일 형식, `429` 과도한 요청, `503` 일시 장애 | 재시도 가능 여부, 중복 제출 방지 키·유효시간, 타임아웃 후 재전송 정책 |
| 방문자 권한 | 비회원 접수 후보. 다른 고객의 접수·첨부파일 조회는 공개하지 않음 | 남용 방지 방식과 접근성, 개인정보 노출 없는 접수 확인 방식 |
| 운영자 권한 | 운영자 조회/변경 기능이 선택된 경우에만 인증·최소 권한 설계 | 계정 발급/회수, 다중 인증, 담당자 구분, 변경 이력·삭제 정책 |
| 저장 후보 | `Inquiry/QuoteRequest`, `Attachment`, `DeliveryAttempt`, `ConsentVersion` 등 필요한 개념만 정의 | 자체 DB와 외부 서비스 중 선택, 보유기간·삭제·백업, 관리자 필요 여부. DBA 참여는 자체 저장 필요 확정 후 |

서버는 브라우저에서 보내는 수신 주소·파일 경로·접수 상태를 신뢰하면 안 된다. 업무 수신처와 자격증명은 서버 설정으로 관리하고 본문·파일·개인정보를 일반 오류 로그에 그대로 남기지 않는 방식을 제안한다.

첨부파일을 받는다면 허용 확장자와 실제 유형·크기 검증, 서버 생성 파일명, 비공개 보관, 권한 있는 다운로드, 악성파일 검사/격리 방식을 설계해야 한다. 원본 파일명을 공개 URL로 연결하는 방식은 피한다. 구체적 제한 수치와 검사 도구는 서비스·호스팅 선택 후 정한다. 이 제안의 보안 근거는 [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)다.

## 6. 기술 대안: 운영 방식 결정 후 선택

기존 스택이 확인되지 않아 아래 2개 후보를 비교했다. 특정 호스팅·유료 서비스·버전은 확정하지 않았다. 공식 문서 확인일은 2026-09-26이다.

| 대안 | 맞는 조건 | 구성 후보·운영 영향 |
| --- | --- | --- |
| A. 콘텐츠 중심 정적 사이트 | 기준 메뉴 위주이며 회사가 텍스트·사진 갱신을 개발 담당자에게 요청하는 방식 | Astro + TypeScript로 페이지를 정적 생성하고 정적 호스팅에 배포. 연락 링크만 있으면 자체 업무 서버·DB 없이 구성. 폼이 필요해지면 외부 접수 서비스 또는 서버 기능을 별도 선택 |
| B. 웹 운영 기능 통합 | 문의 이력·담당자 처리·자료실 등 맞춤 운영 화면이 실제 필요할 때 | Next.js + TypeScript의 웹 화면과 서버 기능을 후보로 검토. 관리자·DB·파일 저장소는 선택 범위에 맞춰 추가. 인증·백업·접수 처리·호스팅 운영 업무가 늘어남 |

Astro 공식 문서는 기본적으로 페이지와 엔드포인트를 빌드 시 생성하며, 요청 시 서버 처리가 필요한 경로에 어댑터를 사용할 수 있다고 설명한다. 따라서 A에서도 선택한 문의 기능을 위한 서버 확장은 가능하다. [Astro on-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/)

Next.js는 Route Handlers로 서버 엔드포인트를 구성할 수 있다. 다만 순수 정적 내보내기 모드에서는 요청 기반 동적 기능을 실행할 수 없으므로 자체 `POST` 접수 기능을 함께 배포하려면 서버 실행 환경 또는 별도 접수 서버가 필요하다. [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers), [Next.js Static Exports](https://nextjs.org/docs/app/guides/static-exports)

**현재 자료에 따른 우선 검토안은 A**다. 이는 기준 메뉴가 콘텐츠 중심이라는 분석에 따른 제안이다. B를 선택할 근거가 될 운영 담당자·이력관리·편집 빈도를 먼저 확정해야 한다. CMS는 콘텐츠 편집 방식의 별도 결정이며, 프레임워크만 고른다고 관리자 기능이 생기지는 않는다.

### 7.2 작업 순서·소유권 제안

1. **PM: 범위·콘텐츠 확정.** 기준 메뉴와 별도 요구의 채택 여부, 운영 시나리오, 현재 회사정보와 원본 사용 권한을 정리한다. 메뉴·에셋 분석 결과를 통합한다.
2. **designer + architect: 디자인·기술 명세.** 페이지 구조·컴포넌트·색상·폰트·모바일 레이아웃과 스택·URL·환경을 설계한다. UI/API 계약이 필요한 경우 함께 확정한다. 기본 정적안이면 서버/DB 단계의 해당 없음 사유를 기록한다.
3. **DBA: 필요한 경우에만 저장 계약.** 자체 접수/운영 데이터 저장을 선택하면 데이터 모델·보유기간·권한·파일 메타데이터·마이그레이션을 확정한다. 외부 접수 서비스를 선택하면 해당 서비스의 저장·삭제·조회 계약을 확인한다.
4. **PM: 프로젝트 초기 구성.** 패키지·잠금 파일·환경·공유 타입 담당자를 지정한다. 실제 파일 경로는 스택 확정 후 TEAM_PLAN에 기록한다.
5. **frontend / backend / dba: 필요한 역할만 병렬 구현.** frontend는 웹 화면·본문·클라이언트, backend는 선택한 접수 API·알림·검증, dba는 지정 ORM·마이그레이션·seed를 소유한다. 공유 설정 동시 수정은 금지한다. ORM 의존 빌드/통합은 DBA 완료 뒤 수행한다.
6. **QA → tester + auditor.** 메뉴·콘텐츠·반응형·접근성·계약을 검증한다. 폼을 채택하면 정상 접수, 검증 실패, 파일 제한, 중복 제출, 수신 실패, 타인 접수 접근 차단을 검증한다. 현재 분석 결과와 구현 검증 결과를 분리 기록한다.
7. **요청된 배포·인수인계.** 미리보기 확인, 회사 문구 승인, 실제 환경 접수·HTTPS 검증, 복원 절차와 운영 담당자 인계. production 반영은 팀 규칙에 따른 해당 배포 승인 범위에서 수행한다.

공수는 페이지 개수만으로 단정하지 않는다. 인증서·정보통신설비 원고 확보, 텍스트 이미지 재작성, 에셋 교체, 폼 첨부·관리자·CMS 선택이 작업량을 좌우한다. 범위와 자료 확보 정도를 확정한 뒤 화면/콘텐츠/운영 기능 단위로 산정해야 한다.

중간 텍스트 확인 명령 1회는 PowerShell의 따옴표 해석으로 Python 구문 오류가 났고, 파일 기반 스크립트로 바꿔 정상 확인했다. 이를 제품 테스트 실패로 해석하지 않는다.

산출물은 이 문서와 재현 가능한 입력 점검 스크립트·점검 JSON이다. `TEAM_TECH_SPEC`은 확정 범위·스택·필요 API/DB 결정 이후 작성할 다음 단계 산출물로 남긴다. 전체 자료의 중복·화질·사용권·제3자 자료 여부는 [에셋 분석](ASSET_AUDIT.md) 및 PM 통합 보고서와 함께 판단한다.
